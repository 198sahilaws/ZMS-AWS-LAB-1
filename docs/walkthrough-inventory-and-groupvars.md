# Code Walkthrough — Inventory & `group_vars`

**Audience:** new engineer joining the ZMS AWS lab.
**Files covered (6):**

```
control-repo/inventory/aws_ec2.yml
control-repo/inventory/group_vars/all.yml
control-repo/inventory/group_vars/os_linux.yml
control-repo/inventory/group_vars/os_windows.yml
control-repo/inventory/group_vars/distro_amazon.yml
control-repo/inventory/group_vars/distro_ubuntu.yml
```

**Prerequisite reading:** `docs/walkthrough-collect-debug.md` (glossary), `FIXES-SUMMARY.md`.

---

## Why this module matters more than its size suggests

These six small files decide **which machines Ansible manages** and **how it logs into each
one**. They are the seam between Terraform and Ansible: Terraform writes EC2 tags, this
module turns those tags into inventory groups, and the groups carry the connection settings.

Three of the worst bugs in this project originated here:

| Bug | Symptom | Root cause |
|---|---|---|
| Wrong login user | Amazon Linux hosts `Permission denied (publickey)` | `ansible_user` defined in two competing groups |
| Wrong file location | Standalone playbooks had **no** connection vars at all | `group_vars/` sat at repo root instead of next to the inventory |
| Windows escalation | `Become plugin sudo is not supported by the Windows exec wrapper` | Global `become` inherited by the Windows group |

Read the "why" sections carefully — most of this file's content is scar tissue.

---

## 0. The critical structural rule: **where these files live**

```
control-repo/
├── ansible.cfg
├── site.yml
├── playbooks/
│   └── ubuntu-mysql.yml
└── inventory/
    ├── aws_ec2.yml          ← inventory source
    └── group_vars/          ← MUST be here, next to the inventory
        └── ...
```

**The rule.** Ansible loads `group_vars/` from **two** locations only:

1. adjacent to the **inventory** source, and
2. adjacent to the **top-level playbook** being run.

**Business rule (plain English):** *Connection settings must load for every playbook, whether
it is run from the repo root or from `playbooks/`. Therefore `group_vars/` lives next to the
inventory, not next to the playbooks.*

**What went wrong when this was violated.** `group_vars/` originally sat at the repo root.
`site.yml` (also at the root) loaded it fine. But `playbooks/ubuntu-mysql.yml` — invoked
directly, or pulled in via `import_playbook` — did **not**, because the root is not adjacent
to that playbook. Those plays therefore ran with **zero connection variables**: no
`ansible_user`, no `ansible_connection`. SSH fell back to the local username (`ansible`) with
no key, producing `Permission denied (publickey)` on hosts that were perfectly healthy.

> **Do not move this directory back to the repo root.** It will silently break every playbook
> under `playbooks/` while leaving `site.yml` working — the worst kind of partial failure.

## 1. `inventory/aws_ec2.yml` — the dynamic inventory

There is no static host list anywhere in this repo. The host list is generated by querying
EC2 on every run.

### 1.1 Plugin declaration

```yaml
plugin: amazon.aws.aws_ec2
```

**What it does.** Declares this file an *inventory plugin config* (not a playbook, not a
static inventory). Ansible matches the `plugin:` key against enabled inventory plugins.

**Dependencies.**
- `ansible.cfg` must have `enable_plugins = aws_ec2`, or the file is ignored entirely.
- The `amazon.aws` collection must be installed (`requirements.yml`).
- `boto3`/`botocore` must be importable — **this is why `collect-debug.sh` probes for them.**
  Without boto3 the plugin returns **zero hosts**, which looks like a tagging or region
  problem rather than a missing Python library.

**Gotcha.** The filename must end in a recognised inventory suffix and be referenced by
`ansible.cfg`'s `inventory =`. Renaming it breaks discovery silently.

### 1.2 Region resolution

```yaml
regions:
  - "{{ lookup('ansible.builtin.env', 'AWS_REGION') | default('eu-west-3', true) }}"
```

**What it does.** `lookup('ansible.builtin.env', 'AWS_REGION')` reads an environment variable
at parse time. `| default('eu-west-3', true)` supplies a fallback — the **second argument
`true`** means "also use the default when the value is *empty*", not merely undefined. Without
it, an env var set to `""` would produce an empty region rather than the fallback.

**Why.** `AWS_REGION` is injected by Terraform into `/etc/ansible/estate.env`, which systemd
loads for the timers. Making the inventory read the same variable keeps **one** source of
truth shared by the inventory, the playbooks (`aws_region` in `all.yml`), and the shell
scripts.

**⚠️ Gotcha — this templating is fragile by nature.** The `aws_ec2` plugin templates *some*
option values, but not all. The equivalent Azure project hit exactly this: its
`include_vm_resource_groups` option was **not** templated, so a `lookup('env', ...)` there
stayed an un-rendered literal string and the inventory returned nothing. The fix was to read
the value from the environment directly. If a `lookup()` in this file ever appears to be
ignored, suspect this class of bug first.

The comment offers the escape hatch: delete the `regions` block entirely and boto3 will pick
up `AWS_REGION`/`AWS_DEFAULT_REGION` from the environment on its own.

### 1.3 Filters — what gets managed

```yaml
filters:
  instance-state-name: running
  tag:ManagedBy: Terraform          # only managed instances
```

**What it does.** Server-side EC2 `DescribeInstances` filters. Both must match (logical AND).

**Business rules (plain English):**
1. *Only running instances are managed.* Stopped/terminated hosts are excluded, so a
   converge doesn't fail trying to reach a machine that is intentionally down.
2. *Only instances Terraform created are managed.* Anything without `ManagedBy=Terraform` is
   invisible to Ansible — a hand-launched instance in the same VPC will never be touched.

**Dependencies.** The tag value is **`Terraform` with a capital T**, set by
`modules/naming/main.tf`:

```hcl
standard_tags = {
  Environment = var.environment
  Owner       = var.owner
  Project     = var.project
  ManagedBy   = "Terraform"      # ← this exact string
  CostCenter  = var.cost_center
}
```

**⚠️ Gotcha — tag matching is case-sensitive on both key and value.** `managedby=terraform`
does not match. An empty inventory graph is almost always *this* or a wrong region — not a
broken plugin. `collect-debug.sh` and `site.yml`'s pre-flight assert both call this out by
name because it wasted time repeatedly.

### 1.4 Addressing

```yaml
hostnames:
  - private-ip-address
compose:
  ansible_host: private_ip_address
```

**What it does.** `hostnames` chooses what the **inventory hostname** is (the string you see
in output and pass to `--limit`). `compose` sets `ansible_host` — the address actually
connected to — using a Jinja expression over host facts.

Note the two different spellings: `private-ip-address` (a **filter/hostname key**, hyphens,
matching the EC2 API) vs `private_ip_address` (a **host variable**, underscores). Mixing them
up is a common first mistake.

**Why private IPs.** The control node lives **inside the VPC** in a private management subnet.
Workload instances have **no public IPs at all**. Private addressing is the only option, and
it also means traffic never leaves the VPC.

**Consequence you will notice immediately.** Inventory hostnames are raw IPs
(`10.188.10.49`), not friendly names. That's why every log line and `--limit` argument in
this project is an IP address. It also means hostnames **change on every rebuild** — never
hardcode them in scripts or docs.

### 1.5 `keyed_groups` — tags become groups

```yaml
keyed_groups:
  - key: tags.OS
    prefix: os
    separator: "_"
  - key: tags.Distro
    prefix: distro
    separator: "_"
  - key: tags.Role
    prefix: role
  - key: tags.Environment
    prefix: env
```

**What it does.** For each rule, Ansible reads the tag named by `key` and creates a group
called `<prefix><separator><value>`. Default separator is `_`, so the last two rules produce
`role_web`, `env_zms` even without an explicit `separator`.

A host with `OS=linux, Distro=ubuntu, Role=web, Environment=zms` joins **four** groups:
`os_linux`, `distro_ubuntu`, `role_web`, `env_zms`.

**This is the core architectural idea of the whole repo.** Groups are the contract between
Terraform and Ansible:

| Group family | Set by (Terraform) | Consumed by (Ansible) |
|---|---|---|
| `os_*` | `compute-linux` → `OS=linux`; `compute-windows` → `OS=windows` | connection settings (`os_linux.yml`, `os_windows.yml`) |
| `distro_*` | `compute-linux` → `Distro=amazon\|ubuntu` | login user (`distro_*.yml`), package manager choice |
| `role_*` | role lists in `terraform.tfvars` | which playbooks target the host |
| `env_*` | `Environment` tag | scoping with `--limit` |

**🔴 The single most important gotcha in this module — `role_*` groups span BOTH operating
systems.**

Terraform assigns roles independently per OS. With
`ubuntu_server_roles = ["db","web","client"]` and `windows_server_roles = ["dc","rodc"]`,
the group `role_web` can contain **Ubuntu, Amazon Linux and Windows hosts simultaneously**.

Consequence: **a playbook must never target a bare `role_*` group.** Doing so sends `apt` at
Windows and `win_feature` at Linux. This actually happened — `windows-iis.yml` targeted
`role_web` and attempted IIS installation against Linux web servers.

**Business rule (plain English):** *Every service playbook targets a role **intersected with**
an OS or distro group.* Ansible's intersection operator is `:&`:

```yaml
hosts: "{{ target | default('role_web:&distro_ubuntu') }}"    # Ubuntu web servers only
hosts: "{{ target | default('role_web:&os_windows') }}"       # Windows web servers only
hosts: "{{ target | default('role_db:&distro_amazon') }}"     # Amazon Linux DB servers only
```

This rule is documented in `orchestrate.yml` so it can't silently regress.

### 1.6 ⚠️ Implicit exclusion of the control node and bastions — read this carefully

Nothing in this file explicitly excludes infrastructure hosts. They are excluded **only
because of which tags Terraform does or doesn't set**:

| Host | `OS` tag | `Role` tag | Lands in `os_linux`? |
|---|---|---|---|
| Linux workload | `linux` | `db`/`web`/… | **yes** — managed |
| Windows workload | `windows` | `dc`/`rodc`/… | **yes** — managed (`os_windows`) |
| Ansible control node | *(none)* | `ansible-control` | **no** |
| Linux bastion | *(none)* | `bastion` | **no** |
| Windows bastion | `bastion` | `bastion` | **no** |

The control node and the Linux bastion are absent from `os_linux` purely because
`modules/ansible-control/main.tf` and `modules/bastion/main.tf` **omit the `OS` tag**. The
Windows bastion is different: it explicitly sets `OS = "bastion"` with a code comment saying
it's so Ansible never targets it — that one is provably deliberate.

**This is a load-bearing property held together by an absence.** If someone "tidies up" the
bastion or control-node modules by adding `OS = "linux"` for consistency, Ansible will
immediately start managing the bastion **and the control node itself** — the control node
would try to SSH to itself and apply the baseline role to its own OS.

> **Assessment:** effective, but implicit and undocumented in the Terraform modules.
> Whether the omission was deliberate design or convenient accident is **not inferable from
> the code — needs confirmation from the original author.** The Azure sibling project handled
> this *explicitly* (an inventory filter excluding `Role=ansible-control`), which is the
> safer pattern. **Recommend adding an explicit exclusion filter here** rather than relying on
> a missing tag.

## 2. `group_vars/all.yml` — estate-wide variables

Applies to **every** host, including `localhost`.

### 2.1 SSH key path

```yaml
ansible_ssh_private_key_file: /etc/ansible/keys/ansible_rsa
```

**What it does.** Tells the SSH connection plugin which identity file to use.

**Why the filename matters.** The comment records a real bug: this was once
`ansible_ed25519` while the Terraform keypair is **RSA**, and `bootstrap.yml` wrote the key
under a *third* hardcoded name. The connect path and the write path disagreed, so every Linux
host was unreachable with `no such identity`.

The fix was twofold: settle on a distro-neutral name, and make `bootstrap.yml` write to
`{{ ansible_ssh_private_key_file }}` — **the variable, not a literal** — so the two can never
drift again.

**Dependencies (a remaining weak point).** Three places reference this path:

1. this variable — the read path
2. `bootstrap.yml` — the write path (now via the variable ✅)
3. `scripts/collect-debug.sh` → `KEY_FILE=` — **still a hardcoded literal ⚠️**

Item 3 can still drift. Flagged in the `collect-debug.sh` walkthrough too.

**Gotcha — ownership, not just path.** The file must be **readable by the user the systemd
timers run as** (`ubuntu`). It was once written `root:root 0600`, so the SSH client couldn't
read it and every host reported `UNREACHABLE`. `bootstrap.yml` now sets owner explicitly, and
`collect-debug.sh` reports `ls -l` on it for exactly this reason.

### 2.2 Region

```yaml
aws_region: "{{ lookup('ansible.builtin.env', 'AWS_REGION') | default('eu-west-3', true) }}"
```

**What it does.** Same env lookup as the inventory, exposed as a play-level variable.

**Why.** Used as the `region=` argument to every `amazon.aws.aws_secret` lookup. Deliberately
mirrors the inventory's logic so both resolve identically.

**Gotcha.** This is evaluated **lazily**, at first reference. A play that never touches a
secret never evaluates it — which is why Linux-only runs work even if the region were
misconfigured.

### 2.3 Secret name

```yaml
ansible_secret_name: "{{ lookup('ansible.builtin.env', 'ANSIBLE_SECRET_NAME') | default('', true) }}"
```

**What it does.** Reads the **name** of the consolidated secret from the environment.

**Why the name travels via the environment.** Terraform and Ansible run on **different
machines at different times**. The secret's name contains a random suffix
(`ss-zms/ansible-credentials-2orkan`) generated at apply time, so it cannot be committed to
Git. Terraform's cloud-init writes it into `/etc/ansible/estate.env`; systemd loads that file
for the timers; this line picks it up.

**Business rule:** *Only the secret's **name** crosses the Terraform→Ansible boundary. The
secret's **value** is fetched at run time by the control node using its IAM role.*

**Dependency chain — memorise this, it explains most "secret" failures:**

```
terraform.tfvars → module.secrets (creates secret)
                 → module.ansible-control cloud-init
                 → /etc/ansible/estate.env   (0640 root:root)
                 → systemd EnvironmentFile=
                 → ANSIBLE_SECRET_NAME env var
                 → this line
                 → aws_secret lookups in os_windows.yml + playbooks
```

**⚠️ Gotcha — the most common false alarm in this repo.** `estate.env` is `0640 root:root`.
Run anything **without `sudo`** and this resolves to `''`, so every secret lookup fails with:

```
Failed to retrieve secret: Parameter validation failed:
Invalid length for parameter SecretId, value: 0, valid min length: 1
```

That message looks like a broken secret. It usually means *you didn't source the env file*.
Always:

```bash
cd /opt/control-repo
set -a; . /etc/ansible/estate.env; set +a
```

### 2.4 The absent variable — a deliberate non-implementation

```yaml
# NOTE: the decrypted secret is deliberately NOT bound to a global variable here.
# A single broadly-scoped `ansible_credentials` dict would put the SSH private key
# and every password in scope for every play ...
```

**What it does.** Nothing — that's the point. This comment documents a variable that was
**removed**.

**History.** There used to be:

```yaml
ansible_credentials: "{{ lookup('amazon.aws.aws_secret', ansible_secret_name, region=aws_region) | from_json }}"
```

One global dict holding the SSH private key, WinRM password, DSRM password, domain-join
credentials, MySQL root password and the ZMS provisioning nonce — **in scope for every play
on every host.** Any `-vvv` run or stray `debug: var=hostvars[inventory_hostname]` would dump
all of them.

**Business rule (plain English):** *Each play resolves only the single secret field it needs,
inline at the point of use, under `no_log`. No variable ever holds the whole secret.*

The replacement pattern, seen throughout the repo:

```yaml
mysql_root_password: "{{ (lookup('amazon.aws.aws_secret', ansible_secret_name, region=aws_region) | from_json).mysql_root_password | default('', true) }}"
```

**Trade-off to be aware of.** This costs one Secrets Manager API call per field per play,
rather than one call total. At this estate's size that's negligible; at hundreds of hosts
you'd want caching. Accepted deliberately in favour of blast-radius reduction.

## 3. `group_vars/os_linux.yml` — Linux connection settings

```yaml
ansible_connection: ssh
ansible_become: true
ansible_become_method: sudo
```

**What it does.** Selects the SSH connection plugin and enables `sudo` escalation for the
`os_linux` group.

**Why explicit** even though `ansible.cfg` also sets `become = True`: group-level settings are
self-documenting and survive `ansible.cfg` changes. (Mild redundancy — but see the Windows
file for why relying on the global was actively harmful.)

### 3.1 The commented-out `ansible_user` — the most important comment in the module

```yaml
# The login user is set PER DISTRO, in inventory/group_vars/distro_amazon.yml
# (ec2-user) and distro_ubuntu.yml (ubuntu). It is deliberately NOT set here:
# defining ansible_user in os_linux too would create a same-level group-var
# conflict that ansible_group_priority does not reliably resolve on ansible-core
# 2.21 ...
# ansible_user: ubuntu
```

**What it does.** Nothing. It is a deliberate **absence**, with an explanation.

**The bug it prevents.** The original design was:

```yaml
# os_linux.yml
linux_login_user: ubuntu
ansible_user: "{{ linux_login_user }}"        # ← defined here

# distro_amazon.yml
ansible_group_priority: 10                     # ← "this should win"
linux_login_user: ec2-user
```

The intent: `distro_amazon` raises its priority so its `linux_login_user` overrides
`os_linux`'s. **It did not work on ansible-core 2.21.** `ansible_user` was defined in
`os_linux`, `os_linux` won the merge, and every Linux host — including Amazon Linux — tried
to log in as `ubuntu`. Amazon Linux has no such account:
`Permission denied (publickey)`, half the fleet unreachable.

**The fix — structural, not priority-based.** Define `ansible_user` in **exactly one place**
per host: the distro group. With no competing definition there is no conflict to arbitrate,
and no dependence on `ansible_group_priority` semantics.

**Business rule (plain English):** *The SSH login user is owned solely by the `distro_*`
groups. `os_linux` must never define `ansible_user`.*

**Gotcha.** Uncommenting that fallback line **reintroduces the bug**. It's there to document
the option for hosts with no `Distro` tag (which Terraform never produces), not as a
suggestion.

### 3.2 The bastion ProxyCommand block — currently dead

```yaml
# ansible_ssh_common_args: >-
#   -o ProxyCommand="ssh -W %h:%p -q ubuntu@{{ bastion_host }}"
```

**Status: dead code, intentionally retained.** Not needed in the current topology — the
control node sits inside the VPC and reaches workloads directly by private IP.

Retained as a documented escape hatch if the control node is ever moved outside the VPC.
Note it references `bastion_host`, which **is not defined anywhere** in the repo — enabling
this line requires supplying that variable too.

## 4. `group_vars/os_windows.yml` — Windows connection settings

### 4.1 Transport

```yaml
ansible_connection: winrm
ansible_port: 5986
ansible_winrm_transport: ntlm
ansible_winrm_server_cert_validation: ignore
ansible_winrm_message_encryption: auto
```

**What it does.** Selects WinRM over HTTPS (5986) with NTLM authentication and disabled
certificate validation.

**Why each value:**

- **5986 / HTTPS** — the listener Terraform's `user_data` creates. (Note EC2Launch v2 also
  creates one; see the `LocalAccountTokenFilterPolicy` incident in `FIXES-SUMMARY.md`.)
- **`ntlm`** — hosts are workgroup members at first contact, before AD exists. Kerberos would
  be preferable once domain-joined but requires a working KDC, which is a chicken-and-egg
  problem during initial build.
- **`ignore`** — the listener uses a **self-signed** certificate and we connect **by IP**, so
  validation would fail on both trust chain and CN. The comment correctly notes production
  should use a trusted cert plus matching DNS name.
- **`auto`** — encrypts the message payload independently of the transport.

**Security note.** `cert_validation: ignore` accepts any certificate and is vulnerable to
MITM. Acceptable inside a private VPC subnet for a lab; explicitly flagged as
not-for-production in the comment.

### 4.2 `ansible_become: false` — a real bug fix

```yaml
ansible_become: false
```

**What it does.** Disables privilege escalation for Windows hosts.

**The bug it fixes.** `ansible.cfg` sets globally:

```ini
[privilege_escalation]
become        = True
become_method = sudo
```

Correct for Linux, **invalid on Windows**. Every Windows play failed at fact-gathering with:

```
Become plugin sudo is not supported by the Windows exec wrapper.
Make sure to set the become method to runas.
```

**Business rule:** *Windows tasks connect as an administrator over WinRM and require no
escalation. `become` is off for the entire Windows estate.*

If a specific task ever needs to elevate a non-admin, set `ansible_become_method: runas` on
**that task**, not globally.

### 4.3 Field-scoped credentials

```yaml
ansible_user: "{{ (lookup('amazon.aws.aws_secret', ansible_secret_name, region=aws_region) | from_json).winrm_username }}"
ansible_password: "{{ (lookup('amazon.aws.aws_secret', ansible_secret_name, region=aws_region) | from_json).winrm_password }}"
```

**What it does.** Each line independently fetches the secret, parses the JSON with
`from_json`, and extracts **one** field via dot notation.

**Why two separate lookups** rather than one shared variable: that shared variable *was* the
removed `ansible_credentials` dict (§2.4). Two API calls is the deliberate cost of not having
a global that holds every password.

**Why `ansible_password` is safe to define here.** Ansible treats it as a magic variable and
**automatically scrubs it** from output and logs.

**🔴 Gotcha — this is why `collect-debug.sh` must never run `ansible-inventory --list`.**
These are **host variables**. `--list` and `--vars` *resolve* host variables, which would
execute these lookups and print **live WinRM credentials** into a diagnostic bundle that gets
pasted into tickets. The debug script uses `--graph` (structure only) specifically to avoid
this. Do not change it.

**Gotcha — evaluated lazily and per-host.** These fire when Ansible first connects to a
Windows host. On a Linux-only run they never execute, so a broken secret configuration can
stay hidden until the first Windows play.

## 5. `group_vars/distro_amazon.yml` and `distro_ubuntu.yml`

```yaml
# distro_amazon.yml
ansible_user: ec2-user
```

```yaml
# distro_ubuntu.yml
ansible_user: ubuntu
```

**What they do.** Set the SSH login user, one file per distro group.

**Why they exist at all.** AMIs ship different default accounts: Amazon Linux has
**`ec2-user`** and no `ubuntu`; Ubuntu has **`ubuntu`** and no `ec2-user`. The user must be
known *before* Ansible connects, so it cannot be auto-detected from facts (facts require a
successful connection first — a chicken-and-egg).

**Why `distro_ubuntu.yml` looks redundant.** It sets `ubuntu`, which used to be the
`os_linux` default. It is **not** redundant: it makes the `distro_*` groups the *single source
of truth*. With `os_linux` no longer defining `ansible_user`, an Ubuntu host would otherwise
have **no** login user at all.

**Note the removed line.** Both files previously carried `ansible_group_priority: 10`. It was
deleted along with the `os_linux` definition — with no conflict remaining, priority is
unnecessary, and leaving it would imply the fix depends on a mechanism that proved unreliable.

**Dependency.** Requires the `Distro` tag from `modules/compute-linux/main.tf`:

```hcl
tags = merge(var.tags, {
  OS     = "linux"
  Distro = each.value.distro      # "amazon" or "ubuntu"
  Role   = each.value.role
})
```

**Gotcha — the tag value must match the filename.** `Distro=amazon` → group `distro_amazon` →
file `distro_amazon.yml`. Changing the Terraform value to `amazonlinux` would silently orphan
this file: the group becomes `distro_amazonlinux`, no `group_vars` file matches, and hosts get
no login user. **Terraform tag values and these filenames are coupled by string equality.**

## Variable precedence quick reference

Where a host is in several groups, Ansible merges group_vars in this order (later wins):

```
all  →  os_*  →  distro_*  →  role_*  →  env_*  →  host_vars  →  -e (extra vars, highest)
```

Groups at the **same depth** are merged alphabetically unless `ansible_group_priority`
intervenes — and as §3.1 documents, that mechanism did **not** behave reliably on
ansible-core 2.21. **Design principle for this repo: avoid same-level conflicts entirely
rather than trying to arbitrate them.**

This is also why the manual override works:

```bash
ansible-playbook playbooks/windows-reset-admin.yml \
  -e ansible_user='.\zsroot' -e ansible_password='...'
```

`-e` beats everything, including the secret lookups in `os_windows.yml`.

## Glossary additions

| Term | Meaning |
|---|---|
| **Keyed group** | Inventory group auto-created from a tag value: `<prefix><separator><value>`. |
| **Intersection (`:&`)** | Host-pattern operator selecting hosts in **both** groups — `role_web:&os_windows`. Mandatory here because `role_*` spans OSes. |
| **`compose`** | Inventory-plugin section defining host vars from Jinja over host facts. |
| **`hostnames`** | Inventory-plugin section choosing what the inventory hostname is (here: private IP). |
| **Magic variable** | Ansible-reserved var that changes behaviour (`ansible_user`, `ansible_connection`, `ansible_password`). |
| **Field-scoped lookup** | Resolving one key from the consolidated secret inline at point of use, under `no_log`. |
| **Lazy evaluation** | Jinja in `group_vars` evaluates on first reference, not at load — so unused lookups never run. |

## Flagged issues

1. **Control node and Linux bastion are excluded from `os_linux` only by the *absence* of an
   `OS` tag.** No explicit filter enforces it. Adding `OS = "linux"` to those modules for
   "consistency" would make Ansible manage the bastion and the control node itself.
   **Recommend an explicit exclusion filter** (the Azure sibling project does this).
   Whether the omission was deliberate — **needs confirmation from the original author.**

2. **`KEY_FILE` in `collect-debug.sh` duplicates `ansible_ssh_private_key_file`** as a
   hardcoded literal. Already drifted once. No mechanism keeps them in sync.

3. **Dead code:** the `ansible_ssh_common_args` ProxyCommand block in `os_linux.yml`.
